# Periodic OMP automatic updates

## Ownership and boundaries

Agents owns install-wide runtime consent, trusted command identity, maintenance, and validated capability publication. This design extends [runtime notification automation](runtime-update-notifications.md) and [harness self-update](harness-self-update.md); it does not touch npm selection or task session recovery. It is the OMP exception to the pinned automation path. [The decision](../../../decisions/2026-10-10-periodic-omp-self-updates.md) records the user-selected configured-channel checking and the in-place risk. Requirements: [OMP periodic updates](../requirements/omp-periodic-updates.md).

## Capability and recipe

`agents.RuntimeUpdateCapabilities` reports OMP as external and manual, and `Controller.automaticUpdateSupported` requires `Managed != nil`. Add an explicit trusted automatic harness recipe to `RuntimeUpdateCapability`, populated only from the built-in `OmpACP.HarnessUpdate` recipe (`omp update`, probe `omp acp`). Automation support requires that recipe, a `RuntimeCandidateUpdater`, the consent store and job store, and an available enabled agent. Do not mark the installation Kandev-managed or infer permission from an npm release source. Other harnesses stay unsupported until they declare this capability.

OMP keeps the runtime identity `omp-acp` returned by `RuntimeUpdateCapabilities`; no `npm:` or `native:` variant exists for it. Revalidation therefore checks the trusted recipe and that the agent is still registered, enabled and available, not a runtime-identity change. Custom argv or configuration cannot acquire the capability. OMP launch, installation, remote preparation and passthrough construction do not change.

## Policy state

Reuse `managedruntime.AutoUpdateStore` and the key `agent_runtime.auto.<agent>`. Add optional fields to `AutoUpdatePolicy`, all defaulting to zero so existing records read unchanged:

- `last_attempt_started_at`: the start time of the background pass that admitted the attempt, written with the running marker.
- `consecutive_failures`: count of failed checks since the last non-failure.
- `paused`: true after a pausing failure.
- `last_change`: attempt (job) ID, previous version, observed version and time of the latest changed result.

`UpdateOutcome` gains optional `update_mode`, `operation`, `observed_version` and `output_excerpt`. OMP outcomes leave `target_version` empty. `Outcome` always describes the latest attempt; `last_change` keeps the latest changed result so a later no-change check cannot erase it. The excerpt is the tail of the existing 64 KiB job output ring buffer, sanitized and cut once when the outcome is persisted: strip ANSI CSI and OSC sequences and C0 and C1 control characters except `\n` and `\t`, normalise `\r\n` and `\r` to `\n`, then keep at most 2 KiB from the end at a rune boundary. Newlines survive so multi-line decline messages stay readable. It is shown as plain text only. The status poll and WebSocket replay therefore carry at most 2 KiB per runtime.

Because OMP attempts about every fifteen minutes, the next no-change or failed check overwrites `Outcome`, while the local provider deletes a delivery claim when no subscriber is connected so that a later replay can retry. `publishRuntimeStatus` therefore publishes the changed notice from `last_change` (its occurrence key built from `last_change`'s attempt ID), not from `Outcome`, so a changed notice that could not be delivered is still replayed after later no-change checks. Pausing-failure notices use `Outcome`, which a pause stops from being overwritten.

`setAgentAutomaticUpdatesLocked` already clears `AttemptedVersion` on an enabled flip. For the harness recipe a saved false-to-true transition also clears `paused` and `consecutive_failures`. It never clears `last_attempt_started_at`, so opting out and in cannot bring an attempt sooner than fourteen minutes after the previous one started; passes run only on fifteen-minute ticks, so keeping the timestamp delays a re-enable by at most one tick. An idempotent true save changes none of them. A true-to-false save leaves `paused` set. The status DTO gains a derived `auto_update_paused` boolean (true only while enabled and `paused`) and `last_change`; the TypeScript `AgentUpdateStatus` mirrors both. The UI keys its paused copy on `auto_update_paused`, never on the outcome status, because `Outcome` is deliberately not cleared by recovery.

## Scheduling

`StartRuntimeUpdateBackground` already runs a readiness-gated first pass and fifteen-minute ticks. `RunRuntimeUpdatePass` branches by trusted capability before the pinned `update_available` gate; pinned behavior is unchanged. An OMP check is eligible when consent is saved, the agent is enabled and available, the policy is not paused, no maintenance job is active, and `pass_start - last_attempt_started_at >= 14 minutes`, where `pass_start` is captured at the beginning of the pass and a negative difference (a clock step back) counts as eligible. The fifteen-minute interval less a one-minute slack absorbs ticker jitter. Both stored and compared times are pass start times, so the marker-write delay cannot stretch the cadence. Gating on the pass start rather than the finish keeps the real cadence at one attempt per tick; gating on the finish would skip every second tick and give roughly thirty minutes. Stable metadata failure and equal or newer installed versions never block a check. Status and Settings reads stay read-only; only the background pass admits execution. The pass runs the interrupted-attempt settlement before admission. Eligibility was read from a status snapshot taken before that settlement, so admission re-reads the policy under the consent mutex and re-evaluates enabled, not paused and the cadence there; a pause written by the settlement (for example a stale marker settled as the third consecutive failure) therefore stops the same pass from admitting a fourth updater.

## Admission and execution

Reuse `AgentUpdateJobStore`, its semaphore, maintenance claims, hard timeout, output flusher, `automaticWorkers`, finish events and refresh callback. Add automatic harness admission without weakening manual `EnqueueHarness`. Admission happens synchronously inside the background pass, not in the worker, so no unadmitted job ever exists.

The pass is already serialised by `runtimeUpdatePassMu`. For an eligible OMP runtime it first checks availability through one admission-only helper, `c.agentAvailable(ctx, ag)`, before taking any lock. The helper is a single-agent check: a nil discovery service or mock mode counts as available, a virtual or disabled agent is unavailable, otherwise it calls `ag.IsInstalled(ctx)` (a cheap executable lookup), a non-context probe error means unavailable, and the function is injectable in tests. The status path does not use it and keeps the cached multi-agent `detectAgents`, which must not run under the consent mutex because status reads take that mutex per target. The pass then tries to take a job-store semaphore slot without blocking; a full semaphore defers the check to the next pass and consumes nothing. It takes `runtimeAutoUpdateMu` as the outermost lock, as the manual path does, and re-reads under it the policy (consent, paused, `last_attempt_started_at`), the trusted recipe and agent enablement, re-evaluating eligibility rather than trusting the earlier status snapshot. It then calls a new store method that, in one `s.mu` critical section, claims the maintenance slot, runs a `beforeStart`-style callback that reads the current agent version and persists the running marker (`Outcome` running with the job ID, `PreviousVersion` and `last_attempt_started_at`), and registers the job in `s.jobs` and `activeByAgt`. This reuses the seam that already runs after the claim under `s.mu` and releases the claim on error, and a database write under `s.mu` already has precedent in the manual path. The lock order `runtimeUpdatePassMu` then `runtimeAutoUpdateMu` then `s.mu` then the maintenance mutex is preserved. A claim refused because maintenance is active, a failed revalidation or a failed marker write releases the slot and the claim and persists nothing, so it records no failure, no pause and leaves the interval unconsumed. Claim, marker and registration being one critical section means no claimant ever sees a held claim with no registered job: a concurrent manual request cannot receive a `MaintenanceConflictError` naming an unregistered ID or a nil job from `EnqueueHarness`. The consent mutex is released before the subprocess; it is never held for it. After the critical section the pass broadcasts `agent.update.started` and starts the worker, which already holds the semaphore slot and releases it when it finishes. The persisted running marker is the admission boundary: an opt-out saved before it prevents the update, and one saved after it stops later checks but cannot undo the running update, which is still probed and recorded.

Because admission is synchronous, the job store never exposes a queued, unadmitted automatic job: `Get`, `GetActive` and `ListAll` see an automatic self-update job only once it is registered with its persisted marker, and a manual conflict can therefore only ever hydrate a job that will broadcast a finish. Guard rejection, a refused claim, a full semaphore and a cancelled pass create no job and broadcast nothing, so the installed-agent card shows nothing for a check that did not run. After admission the job DTO carries `automatic: true`, `update_mode: self_update`, status `succeeded` with operation `update` for a changed result, operation `repair` for a repair result, and operation `up_to_date` for a no-change result, and status `failed` with the existing error text for failures and cancellations. The ws handlers upsert every update event into one job per agent (`upsertAgentUpdateJob` replaces the stored job whenever a different job ID has a newer `started_at`, and the store has no dismissal concept), so a periodic automatic check would replace a finished manual result and the installed-agent card would show its spinner, raw output and "updated successfully". The handler (`lib/ws/handlers/agents.ts`) therefore does not store `agent.update.started` and `agent.update.finished` events for `automatic` self-update jobs unless the job ID is in the adopted record or already held by the store. Dropping those events removes two event-driven consumers, so the handler replaces them explicitly: for every ignored automatic event it calls `refreshRuntimeUpdateStatuses(store, true)`, because `use-agent-runtime-update-statuses.ts` otherwise refreshes only when a terminal job appears in `updateJobs.byAgent` and a running, no-change or failed transition would lag up to the 60-second poll; and for an ignored finished event with status `succeeded` and operation `update` or `repair` it increments a per-agent `runtimeActivationByAgent` counter in the settings slice, which `use-profile-model-capabilities.ts` also consumes, because it otherwise re-runs model discovery only for a new `succeeded` entry in `updateJobs`. Settings reads automatic results from the status API outcome. A manual request that hits the 409 adopts the running automatic job: `hydrateConflict` first records the 409 body's `active_job_id` in `adoptedUpdateJobIds`, a `Record<string, true>` inside `AgentUpdateJobsState` (the slice is zustand with immer and does not enable `Set` or `Map` support), before the GET, so a finish that arrives between the server's snapshot and the browser applying it is still applied; it then stores the job, and the id is removed when the held job is replaced so the record does not grow. The card reads the job's `operation` in more places than `UpdateResult`: `runtime-version-summary.tsx` and the primary button label resolve it through `resolveRuntimeOperation`, and `canApproveAgentRuntimeUpdate` (`lib/agent-runtime-update.ts`) requires operation `update` or `repair` for a self-update, so an adopted `up_to_date` job would read "Up to date" and disable the manual Update action. `resolveRuntimeOperation` therefore ignores `job.operation` when `job.automatic` and `update_mode` is `self_update`, falling back to the preview's operation. `UpdateResult` alone renders the neutral automatic sentence (changed with versions, "OMP reported no version change", validated version, failed, interrupted), as the dialog's single `status` region (`alert` when failed) for every job status, never `runtimeUpdatedSuccess`, `runtimeAlreadyUpToDate` or an "Up to date" label. `UpdateBody` omits the manual phase line for automatic self-update jobs, and `RuntimeVersionSummary` keeps the preview operation label and shows only the automatic job's effective version, so one announcement is made rather than two.

The updater and its probe derive their contexts from the background pass context, as pinned automatic jobs do through `job.context`, rather than from `context.Background()`. Backend shutdown and restore quiesce therefore cancel an admitted update promptly instead of blocking `runtimeBackgroundStop` for `jobHardTimeout`, which sits behind the graceful-shutdown cleanups and `quiesceForRestore`. A cancelled updater is recorded as interrupted. The next `omp update` is itself the repair for a partly applied installation, so an interruption by shutdown or process loss does not pause by itself. It counts as a failed check instead, so repeated interruptions still pause. The host probe swallows cancellation: `hostutility.Manager.probeWithOverrides` turns any probe error, including a cancelled context, into a failed capabilities value with a nil error. After `Probe` returns, therefore, a cancelled pass context classifies the result as `cancelled` regardless of the returned error or `caps.Status`, so a restart during validation is interrupted, not a validation failure that pauses. Only `errors.Is(passCtx.Err(), context.Canceled)` selects `cancelled`; the job context is the hard-timeout child, so a deadline that fires at the edge stays `updater_deadline` and never reads as an interruption.

The updater runs under the job's hard timeout, which starts when the worker begins running it after admission. The probe runs on a context derived from the pass context, not from the updater's hard-timeout context, so a slow updater that used its whole timeout still leaves the probe its full allowance. That allowance is the host manager's own 60-second probe cap, which every probe already inherits, so no separate probe deadline is added. An updater that hits its own deadline is a failed check that counts toward the three-failure pause, like any other updater failure: a stall is the same transient class as an offline error, and nothing distinguishes it from one that died mid-install except that the next `omp update` is the repair either way.

Cancellation must be terminal for the whole updater tree. `runDirectCommand` (`agent_update.go`) reads output through `StdoutPipe`/`StderrPipe` scanner goroutines and waits for them before `cmd.Wait()`. `cmd.WaitDelay` does not release those pipes: `os/exec` closes them after the delay only for copy goroutines that `Cmd` itself owns (non-file `cmd.Stdout`/`cmd.Stderr` writers), and `StdoutPipe` creates none, so after cancel the scanners return only when the last grandchild (Homebrew, mise, Bun, npm) exits. Give `runDirectCommand` an opt-in tree-cancel mode used only by the automatic path: (a) route stdout and stderr through line-splitting `io.Writer`s assigned to `cmd.Stdout` and `cmd.Stderr`, so `cmd.Wait()` alone suffices and `WaitDelay` closes the pipes; (b) on POSIX start the command in its own process group, have `cmd.Cancel` send SIGTERM to the group, and arm a five-second timer (a named constant) that sends SIGKILL to the whole group, stopping that timer when `Wait` returns so a reused process-group ID is never signalled; (c) set `cmd.WaitDelay` to the timer plus one second so the pipes are closed even if a descendant ignores both signals. With Cmd-owned writers `Wait` returns `exec.ErrWaitDelay` when the process exits zero but a descendant keeps the pipes open past the delay; in tree-cancel mode, when the context is not cancelled, that error is treated as success and the worker continues to the probe, because the installation has already changed. The mode crosses the `RuntimeUpdater.RunUpdate` boundary through an optional interface (`RuntimeTreeUpdater.RunUpdateTree`, implemented by `hostRuntimeUpdater` and backed by a new `directCommandExecutor` method). Automatic support requires the updater to implement it; an updater without it makes automation unsupported instead of silently falling back to the pipe-scanner path. On Windows there is no process group here: `cmd.Cancel` kills only the parent and `WaitDelay` closes the pipes, so descendants can survive; that residual is accepted and stated rather than claimed away. The platform-specific group handling lives in build-tagged files (`//go:build !windows` and `windows`), because `syscall.SysProcAttr.Setpgid` and `syscall.Kill(-pid, …)` do not compile on Windows. Manual updates keep the current behavior. Killing the tree mid-install is accepted: the harness updater is the integrity boundary and no rollback exists either way. On POSIX the only residual is a descendant that detached itself (for example with `setsid`); the next check's `omp update` is the repair, and the in-place warning states that an interrupted update may leave the installation changed.

## Outcomes and pause

After a successful `RunUpdate` the worker calls `RuntimeCandidateUpdater.Probe` without publishing, then classifies the result. Outcomes are mapped explicitly rather than copied from `job.Status`:

| Result | Persisted outcome | Capabilities | Pause |
| --- | --- | --- | --- |
| Healthy probe, known version differs from a known previous version | `succeeded`, operation `update`, observed version; update `last_change` | Publish | No; reset failure count |
| Healthy probe, previous version unknown | `succeeded`, operation `repair`, observed version; `last_change` unchanged | Publish | No; reset failure count |
| Healthy probe, same known version | `succeeded`, operation `up_to_date`, output excerpt | Unchanged | No; reset failure count |
| Updater exits with an error | `failed`, output excerpt | Keep previous | Increment count; pause at 3 |
| Updater stopped by its own deadline | `failed`, output excerpt | Keep previous | Increment count; pause at 3 |
| Updater succeeds, probe fails (including an `auth_required` status), times out or reports no version | `failed` | Keep previous | Pause |
| Updater or probe cancelled by shutdown, or running marker found with no worker | `interrupted` | Keep previous | Increment count; pause at 3 |

A probe that reports an unusable or empty version is a validation failure, never a change. The retained output excerpt is what lets an operator see a decline message from `omp update` that exits zero (for example a Nix-owned installation); Settings renders it (see below) so the case is visible rather than silently recorded as success. User copy for no change says OMP reported no version change; it never says up to date. Manual unchanged-version jobs still fail as in [harness self-update](harness-self-update.md).

Open policy check: a probe that reports authentication required proves the new binary started and spoke ACP, and the host probe sees only the Kandev process environment and home, not profile or secret environment. If OMP reports `auth_required` there, every re-enable could pause again after the next successful update. Task 01's smoke therefore runs a credential-less probe fixture and records OMP's actual result; if it confirms that behavior, the `auth_required` row is changed to count toward the three-failure pause without an immediate pause before this design is promoted.

Terminal persistence uses a dedicated automatic hook in place of the DTO `onFinished` path for self-update jobs. `AgentUpdateJob` records a typed automatic result (cause: `changed`, `repaired`, `no_change`, `updater_error`, `updater_deadline`, `validation_failed`, `cancelled`; plus previous and observed versions and the sanitized excerpt) and the job store passes it to a new `onAutomaticFinished` hook. `finishFailed` and `formatUpdateJobError` collapse every cause into status `failed` and a generic timeout string, so the cause is never inferred from the DTO status or error text. `controller.go` wires `onAutomaticFinished` next to `onFinished = retainAutomaticOutcome`. Because an OMP job is `Automatic`, `complete()` currently calls `onFinished` and then removes the active entry; for `self_update` jobs `complete()` calls `onAutomaticFinished` instead, before the active-entry delete (`finishLocked` skips that delete for automatic jobs), and `retainAutomaticOutcome` returns early for `self_update` jobs so it cannot overwrite the typed result with `string(job.Status)` or publish a second status without the paused flag. The hook matches the running marker by job ID, so a late result from an older attempt cannot overwrite a newer one, applies the table's pause accounting, saves the policy, and then publishes the terminal status with the derived `auto_update_paused` and `last_change`, so a pausing-failure notice is not delayed until the next fifteen-minute pass. Persistence is fail-closed through the running marker: if the terminal write fails, the marker remains and `settleInterruptedAutomaticUpdate` converts it to `interrupted` on the next pass, with the table's interrupted accounting. The active entry is still released at that point, as today.

The hook dispatch condition is `Automatic && UpdateMode == self_update`. Manual OMP jobs are also `self_update` but not `Automatic`, carry no typed result or marker, and keep the existing `onFinished` path; a test asserts that a manual OMP finish never calls the hook.

## Manual maintenance

A manual OMP update goes through the same maintenance claim, so it cannot overlap an automatic updater. At the controller, `enqueueAgentUpdate` returns a `MaintenanceConflictError` (HTTP 409 with the active job ID) while an automatic job is active; no second `RunUpdate` runs, and consent and pause are unchanged. The existing update hook (`use-agent-runtime-updates`) already adopts the running job on such a conflict, so the manual control shows the running automatic update's progress rather than an error; no new conflict presentation is needed. A manual OMP update does not change saved consent or a pause. This is an explicit exception to the pinned rule that manual updates disable automation, which exists because a pinned selection invalidates the automatic target. OMP has no selection to invalidate. The manual control and vendor guidance stay reachable for recovery.

## Settings and responsive presentation

Reuse `RuntimePolicyRow`, `useRuntimeAutoUpdatePolicy`, `SettingsRow`, the shared Save/Discard bar, the status store and the existing consent endpoint. The switch is currently gated on `management === "managed"`; extend the gate to rows with `auto_update_supported` or saved consent, so an unavailable OMP can still be opted out. Do not make every manual row automatable.

`RuntimeAction` currently shows the manage link only for `management === "managed"` or `managed_fallback`, and `RuntimePolicyRow` renders `runtimeManualHelp` ("Update it with the installation owner's supported tools") under every non-managed row. For a supported or consented OMP row, show a link to the installed-agent card (`#installed-agent-<name>`, where OMP's manual update control lives) with an OMP-specific localized label (not "Manage versions": OMP has no version selection) when `hasRuntimeControl` is true and the user can manage, keep the vendor guidance link, and replace `runtimeManualHelp` with the OMP paragraph so it does not contradict the switch.

The OMP row renders its own explanatory paragraph (checks follow the configured channel at an interval of about fifteen minutes; updates are in place; Kandev cannot roll back) and points its switch's `aria-describedby` at it. The shared paragraph keyed `runtime-automatic-help` describes validated activation and stays scoped to pinned managed rows. Show separate localized messages for changed, repair (the validated version, no claimed change), no change, running, failed, interrupted and paused, with previous and observed versions and no target. Show the latest `last_change` (previous to observed versions) as its own line until a later change replaces it, and show a non-empty `output_excerpt` for no-change and failed results as plain text inside a native collapsed `<details>` disclosure. A probe that reports authentication required is a validation failure, so a credential-less install pauses after its first check; signing in and the off, save, on, save sequence resume it. See [UI-01 and UI-02](../../../plans/omp-automatic-updates/plan.md#ascii-ui-preview).

Desktop keeps the compact row with help and results wrapping beneath it. Phone keeps the stacked row with the visible switch, the manual update link, shared Save/Discard, one page scroll owner, 44px touch targets and no horizontal overflow. No new overlay or hover-only warning. The nearest exemplar is `mobile-agent-runtime-notifications.spec.ts`. All new strings use `t()` in every shipped catalog; generate Traditional Chinese with `pnpm run i18n:zh-hant`. Do not translate control-flow values.

## Notification compatibility

`publishRuntimeStatus` currently maps a terminal outcome's `TargetVersion` to the notice `Version`, and notification delivery rejects an empty version. Extend `agents.RuntimeUpdateNotice` and the service payload with explicit `update_mode`. A changed result uses the observed version. A pausing failure carries the previous known version as context; the service must accept a self-update notice with no version. The occurrence key uses the immutable attempt ID so reconnect cannot duplicate it.

Publish a notice only for a changed result (operation `update`) or a result that paused automation (`auto_update_paused`). A repair result (previous version unknown), no-change results and failures that did not pause stay in Settings. `runtimeUpdateMessage` and `useUpdateAvailableToast` select copy by mode, never by display name or translated text, and OMP notices never offer rollback or default recovery.

The local provider builds its WebSocket payload from a fixed key list in `notifications/providers/local.go`, so `update_mode` must be added there or the frontend never sees it. A map-key whitelist is not found by a symbol reference search, so this file and `local_test.go` are named explicitly in the work orders. Extend the frontend notification type definitions in `lib/state/slices/ui/types.ts` and `lib/types/backend.ts`.

## Verification

Controller tests use a deterministic clock and deferred runner/probe gates rather than fifteen-minute sleeps. They cover cadence on the pass start time, across restart and with a clock step back, no stable gating, every row of the outcome table (including the typed cause reaching the hook for each and an `auth_required` probe pausing), pause and saved re-enablement, restart settlement including a stale marker settled as the third consecutive failure admitting nothing in the same pass, the synchronous admission section (a full semaphore, a refused claim, guard rejection on consent, availability or maintenance, each creating no job and broadcasting nothing, the job list and `GetActive` never exposing an unadmitted job, and the availability helper working through an injectable function outside the consent mutex), opt-out after admission, cancellation by shutdown that stops promptly even when the fixture updater forks a grandchild holding the pipes, a cancellation during the probe recorded as interrupted and not paused, a deadline at the updater edge staying `updater_deadline`, a slow updater still leaving the probe its full cap, an interrupted result that does not pause until the third, excerpt cap and sanitizing, the terminal publish carrying paused state, terminal persistence failure, manual-update independence, and no overlapping updater between manual and automatic maintenance. Frontend tests cover the ws handler dropping automatic self-update events unless the job is adopted or already held while still refreshing statuses and bumping the activation counter, the adopted-id record being set before the GET and cleared on replacement, and the card helpers ignoring an automatic job's operation. Assert actual updater calls and published catalogue contents, not copied DTO fields. Run existing pinned automation and manual harness regressions together.

Desktop and mobile E2E use the existing runtime-awareness fixture pattern to prove saved consent, the warning, results, paused recovery and reload. Backend coverage proves actual command scheduling; route-intercepted UI tests do not claim real OMP execution. An implementation smoke exercises a disposable updater and probe fixture through the real controller and records the changed, no-change and opted-out cases. No model prompts, real installation mutation or user database are used.
