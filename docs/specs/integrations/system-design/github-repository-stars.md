# GitHub Repository Stars System Design

## Context and boundaries

The integration system owns the authenticated GitHub client and provider calls. The plugin marketplace and installed-plugin settings surfaces consume this capability through the existing GitHub API client and plugin repository metadata. GitHub's REST starring contract provides `GET /user/starred/{owner}/{repo}` for status, `PUT /user/starred/{owner}/{repo}` for starring, and `DELETE /user/starred/{owner}/{repo}` for unstarring. Mutation endpoints require an empty request body and return success without a response payload.

Personal starring uses the separate OAuth App connection defined by [ADR-2026-09-18-github-personal-star-oauth](../../../decisions/2026-09-18-github-personal-star-oauth.md). The existing GitHub App user-to-server personal flow and App installation credentials remain separate and are not star fallbacks.

## Dedicated OAuth App configuration

The typed startup catalog owns three deployment settings: YAML `github.personalStarOAuth.clientId` with environment alias `KANDEV_GITHUB_PERSONAL_STAR_OAUTH_CLIENT_ID`, YAML `github.personalStarOAuth.clientSecretRef` with environment alias `KANDEV_GITHUB_PERSONAL_STAR_OAUTH_CLIENT_SECRET_REF` and sensitivity `true`, and YAML `github.personalStarOAuth.callbackURL` with environment alias `KANDEV_GITHUB_PERSONAL_STAR_OAUTH_CALLBACK_URL`. Environment values override YAML according to the stable configuration source contract. `clientId` and `callbackURL` are required together with the secret reference to enable the feature; callback URL must be absolute HTTPS in production. Its origin is authoritative for the OAuth callback and return-path origin; no absent web-origin setting is consulted. Reverse-proxy deployments must publish exactly that configured origin, with standard default-port normalization only.

`clientSecretRef` must use the protected internal deployment-secret namespace `kandev-runtime:github-personal-star:client-secret:<version>`. It is not a row in the user/workspace `secrets` table. A deployment-owned `deployment_secret_refs` store records the immutable reference, encrypted value, `installation_id`, closed secret-class enum, version, created/revoked timestamps, and rotation state. The installation ID and deployment root public key are generated together once during bootstrap, persisted in deployment-owned metadata; the private installation key is root-owned with mode `0600`, while the public key is backend-readable. They are supplied as the `DeploymentIdentity` root of trust; neither is request-derived, user-configurable, or writable through database/user APIs. The resolver accepts only exact references whose immutable installation ID equals the current deployment identity and whose class is exactly `github-personal-star-client`, runs without request identity during provider startup, and rejects missing, cross-installation same-class, foreign/user-owned, deleted, revoked, malformed, or class-mismatched references before reveal. A provisioning-only writer can create or revoke rows but cannot update, copy, move, or mutate reference, installation ID, or class. No browser/API/user-secret route can list, reveal, copy, move, select, or create these records.

Operators use the dedicated `kandev deployment-secret github-personal-star provision|revoke` CLI as a root-only process over a separate root-owned Unix socket. The socket parent is root-owned mode `0700`, the socket is root-owned mode `0600`, and the supervisor requires `SO_PEERCRED` UID `0`; the backend service cannot dispatch provisioning RPCs. The socket exchange is one request per connection: the CLI first sends a challenge frame containing exactly `{version:1, domain:"kandev-deployment-secret", action:"challenge", installation_id, client_nonce}` where `client_nonce` is exactly 32 random bytes encoded as RFC 4648 unpadded standard Base64 and must pass strict decode/re-encode equality; the supervisor returns one response frame containing exactly `{version:1, domain:"kandev-deployment-secret", challenge_id, challenge, expires_at}` where `challenge_id` and `challenge` are each 32 random bytes encoded with the same strict unpadded Base64 and `expires_at` is a UTC RFC3339Nano timestamp with `Z`. Both challenge frames use a four-byte unsigned big-endian length followed by 1..65536 bytes of RFC 8785 JCS UTF-8 JSON, with no trailing bytes; the CLI then sends the signed request frame and half-closes its write side, and the supervisor returns one bounded JCS result frame before closing. The signed request frame is four-byte unsigned big-endian envelope length (1..65536), exactly that many JCS envelope bytes, four-byte unsigned big-endian signature length (exactly 86), and exactly 86 unpadded-base64 ASCII signature bytes. Every Base64 field uses strict RFC 4648 decoding and must satisfy `RawStdEncoding.EncodeToString(decoded) == received`, rejecting non-zero unused bits, padding, alternate alphabets, and malformed lengths. The frame must end at the declared boundary with EOF; truncated lengths, mismatched lengths, concatenated frames, trailing bytes, and oversized values are rejected. The envelope rejects duplicate keys and must round-trip parse/re-serialize byte-identically. Its action-specific schemas are exact: `provision` requires `{version:1, domain:"kandev-deployment-secret", action:"provision", installation_id, secret_class:"github-personal-star-client", reference_version, ciphertext_b64, ciphertext_digest, nonce, challenge_id, challenge}`; `revoke` requires `{version:1, domain:"kandev-deployment-secret", action:"revoke", installation_id, secret_class:"github-personal-star-client", reference_version, nonce, challenge_id, challenge}` with neither ciphertext field present. The envelope `nonce` must decode byte-for-byte equal to the challenge request's `client_nonce`, and `challenge` must decode byte-for-byte equal to the issued challenge; `challenge_id` must identify that response. Provision ciphertext is canonical unpadded base64 of a length-bounded encrypted payload, and its digest is exactly lowercase hexadecimal SHA-256 of the decoded ciphertext. The detached signature uses Ed25519 over the exact ASCII prefix `kandev-deployment-secret/v1\0` concatenated with SHA-256(canonical-envelope-bytes), encoded as exactly 86 characters from `[A-Za-z0-9+/]` with no padding; the supervisor verifies the signature with the bootstrap public key before invoking the writer. It recomputes and compares the provision digest, rejects duplicate/non-canonical fields, cross-action fields, oversized payloads, digest mismatch, substituted challenges, and any mutation before the sole writer call. The supervisor issues and atomically consumes the 60-second challenge identified by `challenge_id`, and binds it to the peer UID, installation ID, client nonce, challenge bytes, and exactly one subsequent signed request. The root CLI owns challenge/request transport and signing; `DeploymentSecretProvisioner` owns the only writer call. Forged, tampered, replayed, stale, wrong-peer, wrong-socket, wrong-installation, and HTTP/WebSocket dispatch attempts fail closed. Rotation creates a new version, updates the typed startup setting, restarts the provider, verifies resolution, and then revokes the prior version after existing connections remain refreshable or are explicitly re-consented.
For `provision`, `ciphertext_b64` is a canonical unpadded-Base64 encoding of a UTF-8 JCS sealed envelope `{version:1, algorithm:"AES-256-GCM", key_id, nonce_b64, ciphertext_b64}`. `nonce_b64` is exactly 12 random bytes with strict RFC 4648 RawStdEncoding; `ciphertext_b64` is the AES-GCM ciphertext including its 16-byte authentication tag, also strict RawStdEncoding. The root CLI obtains the deployment master key identified by `key_id` through the existing `MasterKeyProvider`, encrypts the operator's plaintext before signing, and sends only this sealed envelope. The supervisor validates the envelope, key identity, nonce length, ciphertext/tag minimum, and JCS canonicalization; `DeploymentSecretProvisioner` stores the sealed value and resolver decrypts it through the same `MasterKeyProvider`, failing closed on authentication or key-identity errors. Revoke has no sealed payload.
The existing multi-tenancy master-key contract remains unchanged. `DeploymentMasterKeyring.OpenExisting(cfg.ResolvedDataDir())` opens the existing `master.key` read-only and exposes stable ID `legacy-master-key-v1`; it never generates or rotates a key. Backend and CLI use the same recorded root; wrong/missing/invalid roots or IDs fail without filesystem mutation. Restart tests prove existing-key resolution.

Runtime archives stay daemon-free for desktop/Docker. Linux publishes `kandev-deployment-secretd-linux-x64.tar.gz`/`-linux-arm64.tar.gz` with daemon/unit/checksums; release uploads them. Installer manages only `kandev-deployment-secretd.service`, never `kandev.service`. Non-Linux rejects it.

Composition root injects `OpenExisting(cfg.ResolvedDataDir())` into `github.Provide`, registers `githubCleanup`, once-guards a local owner for failures, then transfers to `Services.GitHubCleanup`. Shutdown drains `StarSecretCleanupRunner` before resolver close.

Missing or invalid settings fail closed during GitHub provider startup: the backend remains available, connection status reports incapable, and start/reconnect returns the existing configuration-unavailable error without attempting OAuth. The `github` provider owns validation and resolution during `Provide`; the secret is never returned to the browser. A backend running as UID 0 is unsupported: it would satisfy the same socket peer check as the operator CLI, so such installs report `available=false` with no socket or provisioning side effect.

## Dedicated personal star connection

Per-user connection and lifecycle rows use `(workspace_id, user_id)`; lifecycle revision and credential generation are upserted before every consent. Disconnect increments both, creates an inactive tombstone if needed, and deactivates the connection. The workspace-wide `github_personal_star_workspace_lifecycle.deleted_at` fence serializes starts, flow creation/claim, and connection commits with token cleanup; cleanup sets it before removing per-user rows, so late consent cannot recreate state or commit credentials. E2E reset clears the fence when reusing a workspace. Connections hold GitHub identity, normalized scopes, `public_repo` capability, status, generations, timestamps, and reconnect outcome. Encrypted access/refresh tokens remain in the existing secret store under generation-specific IDs referenced by the row; scope metadata stays non-secret.

A typed deployment configuration supplies the dedicated OAuth App client ID, encrypted client-secret reference, canonical callback URL, and rotation owner. Rotation replaces the client-secret reference through the existing secret/configuration lifecycle; it never edits user connection rows or exposes the secret to the browser. The dedicated flow owns its state/PKCE records and callback route, for example `/api/v1/github/user/starred/oauth/callback`, and does not use the existing App-registration ID invariant or `PersonalAuthService` flow bound to `WorkspaceConnection.AppRegistrationID`.

The authenticated connection lifecycle is explicit: `POST /api/v1/github/user/starred/connection/start` accepts `{workspace_id, return_path}` after controller and service workspace authorization and returns `{authorization_url, state_expires_at}`; it supports both first consent and reconnect and never returns tokens. When authentication is enabled, start additionally requires a real browser `SessionID`; PAT, internal, token-only, and other identities with an empty session ID are rejected before state creation. `return_path` must be an absolute same-origin path under Settings > Plugins, with no external origin, scheme, credentials, or fragment. The browser navigates to the URL. The callback parser decodes the query exactly once and rejects malformed percent-encoding, unknown keys, empty values, repeated keys, or missing keys. The complete accepted multimap is either `{state:[non-empty], code:[non-empty]}` or `{state:[non-empty], error:[non-empty], error_description?:[one non-empty], error_uri?:[one non-empty]}`; `state`, `code`, and `error` each have cardinality exactly one, `error_description` and `error_uri` are allowed only on the error branch and at most once, and no other provider keys are accepted. For `error=access_denied` or another validated provider denial, it consumes the unexpired state before token exchange and redirects to the preserved return path with `star_connection_outcome=declined`. The callback redirects successful replacement with `star_connection_outcome=connected`, reduced scope with `star_connection_outcome=insufficient_scope`, and verified exchange/persistence failures with `star_connection_outcome=failed`. The redirect builder parses the stored return path, removes any prior `star_connection_outcome`, preserves its non-reserved query parameters, and appends exactly one URL-encoded outcome parameter. Wrong-session, cross-workspace, wrong-user, wrong-flow, replayed, expired, and PKCE-mismatched callbacks return the existing authorization error without redirect or token exchange. `DELETE /api/v1/github/user/starred/connection` accepts `{workspace_id}` and explicitly disconnects the current user's dedicated connection: it atomically increments the dedicated lifecycle revision and credential generation, marks the row inactive, invalidates all unclaimed flows fenced to the prior revision, queues owned secrets for cleanup, and leaves repository stars untouched. Any callback that started before disconnect therefore fails the revision fence and cannot reactivate the connection. Start, callback, and disconnect never use or require a workspace App registration.

The dedicated start flow requests `scope=public_repo` and `code_challenge_method=S256`. Its one-time state row contains flow kind `github-personal-star`, a 256-bit random URL-safe state, only `state_sha256` (the lowercase hexadecimal SHA-256 digest of the raw state), workspace ID, Kandev user ID, authenticated session subject, nullable authenticated session ID, expected dedicated lifecycle revision and credential generation captured at start, high-entropy PKCE `code_verifier`, its derived S256 challenge, redirect URI, validated same-origin return path, creation/expiry, and consumed-at. The raw state is never persisted, logged, or returned in callback errors; lookup hashes the presented state once and compares only the digest. The verifier is generated server-side, never returned except through the provider authorization request's derived challenge, and is stored only in the protected state record. The store exposes `ClaimForExchange(state, identity, now)`: one transaction conditionally locks the unexpired, unconsumed row by `state_sha256`, verifies all binding fields, reads the verifier and challenge into callback memory, sets `consumed_at`, sets both persisted PKCE fields to NULL, commits, and returns the verifier exactly once; rollback returns no verifier. Two concurrent claims yield exactly one success, and the committed row contains neither verifier nor challenge. The callback then sends only the returned in-memory verifier to the token endpoint. With authentication enabled, the session subject and session ID are captured from the current identity; callback requires both exact values and the same user ID. With authentication disabled, the middleware's synthetic authenticated default identity binds the state to `auth-disabled:<userID>` as the session subject, stores a null session ID, and callback must match that exact user ID and synthetic subject without requiring a session ID. The callback verifies flow kind, workspace, identity, redirect URI, lifecycle revision, credential generation, PKCE verifier, and unconsumed state through `ClaimForExchange`, then exchanges the code. The replacement metadata CAS also requires the same lifecycle revision and generation; a disconnect fence therefore rejects a callback that began before disconnect, and any newly staged secrets are compensated. Wrong-session, same-user/different-session, cross-workspace, wrong-user, wrong-flow, replayed, expired, disconnected, and PKCE-mismatched callbacks are rejected without token exchange or persistence. Callback verification exchanges the code, extracts and normalizes the returned scope, verifies the authenticated GitHub user, stages generation-specific access and refresh secret IDs, and atomically CAS-writes the new metadata, generation, and IDs. If the metadata commit fails, only staged secrets are compensated. After a successful commit, superseded secret IDs are recorded in a durable cleanup queue and deleted by the cleanup worker; failure to delete them does not affect the new connection. Refresh preserves the last granted scopes and generation relationship. Historical rows with missing or unknown scope metadata are insufficient. Reconnect is preserve-and-remain-usable: starting a replacement does not invalidate the current valid row; failed, declined, expired, disconnected, or reduced-scope callbacks leave the old row, secret IDs, status, and generation unchanged. Replacement occurs only after a verified callback grants `public_repo` and all new persistence succeeds. With no valid prior row, the capability remains unavailable.
The OAuth callback validates the presented `state` before hashing: it must be exactly RFC 4648 `RawURLEncoding` of 32 decoded bytes, with no whitespace, padding, standard-Base64 characters, percent-decoded non-ASCII, or alternate textual encoding. The exact received canonical string is hashed without trimming, normalization, or re-encoding; start emits that same canonical string and all malformed forms fail before digest lookup.
The callback parser retains the raw query spelling for each parameter while validating the multimap. For the `state` parameter it rejects raw values containing `%` or `+`, decodes the raw value exactly once, requires `RawURLEncoding.EncodeToString(decoded) == decodedText`, and hashes only that validated decoded text. Thus percent-encoded URL-safe characters, plus-space forms, and alternate Base64 spellings fail before digest lookup; the parser still applies the general one-decode rule to all other accepted fields.
`ClaimForExchange` enforces the PKCE pair before committing the claim: the verifier must satisfy RFC 7636 length and unreserved-character grammar, the stored challenge must satisfy strict `RawURLEncoding`, and `RawURLEncoding(SHA-256(verifier))` must equal the stored challenge byte-for-byte. Missing or tampered verifier/challenge pairs cause rollback and no token exchange; the claimed verifier is sent to the provider only after this validation succeeds.
The callback controller exposes a dedicated `ParseGitHubStarCallbackRawQuery(rawQuery)` seam before framework query helpers or state lookup. It receives the untouched HTTP query bytes, splits parameter pairs without decoding, applies exact cardinality/allowed-key validation, preserves raw spelling for `state`, then performs the single decode and canonical checks above. Handler vectors prove the canonical `$STATE&code=%252F` one-decode case and pre-lookup rejection of percent-encoded `state`, literal `+`, padding, malformed escape, duplicate `state`, and mixed `code`/`error`.

Workspace deletion records every generation-specific access and refresh secret in the same durable cleanup queue before deleting the connection row. The queue stores owner workspace/user, secret ID, kind, generation, attempt count, next-attempt time, claim lease, and terminal status. `StarSecretCleanupRunner` is a mandatory GitHub-runtime component created by `Provide`, started before backend readiness, and stopped by the GitHub runtime `Stop` path with a cancellable timer and waited goroutine. It claims due records transactionally with a lease, retries with bounded exponential backoff, survives process restart through durable records, and retains terminal failures under the documented retention policy for operator diagnostics. Concurrent workers cannot claim the same record; shutdown waits for the current deletion attempt and releases unfinished leases.

The authenticated connection-status contract is `GET /api/v1/github/user/starred/connection?workspace_id=...`. It returns `{user_id, credential_generation, active, capable, reconnect_required, available}` for the current Kandev user and workspace, without token material. `available` is false when the deployment lacks the supported root daemon/configuration; in that case backend readiness is preserved, no OAuth/start/provisioning request is accepted, and the frontend renders no star control or actionable CTA. `credential_generation` changes after replacement or disconnect; `active` and `capable` describe the committed row. The frontend fetches this status before repository hydration and scopes by all returned fields.

Connection status and CTA truth table:

| `available` | `active` | `capable` | `reconnect_required` | Meaning | UI |
| --- | --- | --- | --- | --- | --- |
| false | any | any | any | Unsupported deployment or unavailable configuration | Omit star/CTA; no start request |
| true | false | false | false | No usable grant and no prior valid generation (first consent, disconnect, or declined consent) | Show `Connect GitHub`; never assert unstarred |
| true | true | true | false | Valid dedicated connection | Hydrate status and show star/unstar controls |
| true | true | false | true | Unknown/reduced scope | Show `Reconnect GitHub`; never assert unstarred |
| true | true | true | true | Prior generation valid, reconnect pending | Keep star controls plus `Reconnect GitHub` |
| true | false | false | true | No usable grant but a prior valid generation exists (replacement failed or was declined) | Show `Reconnect GitHub`; never assert unstarred |

The callback outcome query is navigation-only and untrusted. The UI immediately removes `star_connection_outcome` with `history.replaceState` and uses it only to trigger a refetch of connection status; it never announces a localized success, decline, or failure from the query. Star/CTA rendering and any status feedback derive solely from the freshly fetched scoped connection tuple. Duplicate, unknown, empty, or stale outcome values are ignored after URL replacement and cannot bypass the truth table. `reconnect_required` is a backend-derived invariant: false before a first successful consent, true once a previously valid generation exists without a usable `public_repo` grant; never inferred in the UI. Any tuple not listed renders the non-assertive `Connect GitHub`/`Reconnect GitHub` CTA and never asserts unstarred.

## Components and contracts

- The controller exposes the connection-status endpoint plus three JSON repository endpoints with explicit workspace identity: `GET /api/v1/github/user/starred/connection?workspace_id=...` returns the current user's non-secret generation/capability state; `POST /api/v1/github/user/starred/status` accepts `{workspace_id:string, repository_urls:string[]}`; `PUT /api/v1/github/user/starred` and `DELETE /api/v1/github/user/starred` accept `{workspace_id:string, repository_url:string}`. Repository status accepts at most 100 raw URLs in a 4 KiB body; all provider lookups share a 30-second deadline, and unresolved results remain `null` on provider failure or timeout. Responses are `{states:{canonicalOwnerRepo:true|false|null}}`. Mutation responses are `{starred:true|false}`.
- The dedicated connection service resolves only `github_personal_star_connection` rows with active status and `public_repo`; it rejects GitHub App installations, GitHub App user-to-server connections, missing star connections, and insufficient scopes. It stays separate from `CredentialPurposePersonalWrite`.
- Every endpoint requires a non-empty `workspace_id`. The controller validates the request and the service entry points independently call `Service.authorizeWorkspaceAccess(ctx, workspaceID)` before credential resolution, repository parsing side effects, or provider calls. Missing or foreign workspace IDs return the existing authorization error shape.
- One strict parser consumes raw repository URLs at the backend boundary and is reused by frontend conformance vectors. It requires HTTPS, exact case-insensitive `github.com` hostname with no credentials or port, no percent-encoding, exactly two non-empty path segments, and no query or fragment. Owner must match ASCII `[A-Za-z0-9](?:[A-Za-z0-9-]{0,37}[A-Za-z0-9])?`; repository must match ASCII `[A-Za-z0-9](?:[A-Za-z0-9._-]{0,98}[A-Za-z0-9_-])?` (a trailing hyphen is valid; a trailing dot is not). A final `.git` is removed once before repository validation; `repo.git.git` is invalid. Canonicalization lowercases both segments with ASCII case folding. Unicode, dot-only, empty, traversal-like, encoded, confusable, and out-of-grammar names are rejected identically by Go and TypeScript using shared vectors.
- `apps/web/lib/api/domains/github-api.ts` owns typed calls with `workspace_id` and raw repository URLs. A plugin-star hook first loads connection status, then stores state by `(workspaceId, userId, personalCredentialGeneration, canonicalOwnerRepo, active, capable, reconnectRequired)` and maintains a per-key request epoch. Status and mutation responses apply only when their connection-status snapshot and epoch still match; a mutation increments the key epoch before sending and commits only its confirmed response. The user ID and connection generation are part of the request scope and response fence.

Test-only provider contract: `MockClient` implements every star client method and accepts per-workspace/user repository state plus injected status/mutation failures. E2E-only routes expose dedicated connection setup, callback outcome (connected/declined/insufficient scope/failed), and provider state/failure controls through `helpers/api-client.ts`; route registration requires both the E2E profile selector (`KANDEV_E2E_MOCK=true`) and the mock client, so `KANDEV_MOCK_GITHUB=true` alone in a production-profile process cannot mount them. Reset clears these controls with the connection and secret rows. Authenticated E2E tests use explicit admin/browser contexts after auth restart and exercise the controls through the backend, not direct production-store mutation.
- `MarketplaceEntryRow`, the installed `PluginRow`, installed-plugin detail's `PluginRepoLink`, `canvas-marketplace-detail.tsx`, and `CanvasInstallDialog` render the shared star control using their explicit owning/selected workspace ID. When connection status is inactive or incapable, the control remains non-assertive and exposes a localized `Connect GitHub`/`Reconnect GitHub` CTA; when it is capable with `reconnect_required`, it keeps actionable star controls and adds a separate localized reconnect CTA. Provider-unknown or failed hydration omits the control. It never claims unstarred state for an incapable or unknown connection. The control is separate from repository navigation and row overlay links. It derives `isTouchContext = isMobile || !isFinePointer` from the existing responsive hook: only `!isTouchContext && isFinePointer` uses the existing 24px compact inline control; all touch contexts use a minimum 44px target.

1. The plugin settings page derives eligible raw GitHub repository URLs from visible marketplace entries, installed plugin rows, installed-plugin detail, and the Settings > Plugins Canvases detail.
2. The hook fetches the authenticated connection status, captures workspace, authenticated user ID, generation, active, capable, and reconnect-required state, then hydrates only when active and capable; it reuses matching cached states immediately and requests missing or stale URLs through the bounded status endpoint.
3. A status response merges only returned keys in the same connection-status snapshot and epoch. Unknown (`null`) keys remain non-assertive rather than being rendered as unstarred.
4. Clicking the control increments the repository epoch, disables that key, and sends `PUT` or `DELETE` through the dedicated strict personal GitHub client. A confirmed response updates all mounted rows sharing the scoped key.
5. Workspace or GitHub-account changes invalidate the prior scope and clear visible state before fetching connection status. Reconnect completion refetches connection status before hydration. A late response from the old workspace/user/generation/capability scope is discarded.
6. If the dedicated star connection lacks `public_repo`, the backend returns the existing insufficient-scope provider error. The frontend keeps the optional control non-assertive and leaves the dedicated personal reconnect path available; no star action is retried through an App identity.

## Failure and recovery

The backend maps unavailable, insufficient-scope, or failed GitHub calls to the existing authenticated-provider error boundary. The frontend catches status and mutation failures, leaves state unchanged, and neither toasts nor replaces the marketplace/installed list with an error state. A failed initial status leaves the control unknown or omitted, never a false unstarred claim; a later refresh or completed re-consent retries it.

A failed reconnect never invalidates a previously valid connection. A successful mutation is authoritative for the scoped cache; a failed one restores the prior actionable state and retains no optimistic value.

On transaction commit errors, reconcile the lifecycle and connection row before compensation; queue only staged secret IDs no longer referenced, and retain secrets if reconciliation fails.

## Permissions and security

The backend uses the current request identity to select the user's dedicated personal OAuth App connection and verifies active workspace membership in both the controller and service entry points. It does not require a registered workspace repository for public catalog entries. GitHub App installation identities and existing GitHub App user-to-server connections cannot perform this user-attributed operation, and no fallback changes the actor. Foreign-workspace requests and requests without a dedicated personal connection or `public_repo` capability fail closed.

Raw repository URLs are validated at both UI and HTTP boundaries. Arbitrary GitHub API paths are never accepted. The browser never receives or stores a PAT, OAuth token, App token, or `gh` credential.

## Persistence and observability

GitHub owns star persistence. Kandev stores dedicated OAuth App token material only as generation-specific encrypted secret IDs; scopes, capability, status, user identity, and credential generation stay non-secret connection metadata. Workspace deletion performs idempotent cleanup of every generation-specific star secret before or with row deletion. The E2E reset operation owns star connection, OAuth-flow, cleanup-queue rows, and generation-specific secrets transactionally per workspace; its two-workspace test proves no cross-worker leakage. The frontend keeps only an in-memory star cache scoped to workspace, authenticated user, credential generation, and canonical repository. Failures use existing GitHub integration logging and metrics without repository names or user-specific labels.
