# Task 06: Manifest, config schema, and package validation

## Intent

Finalize `manifest.yaml` to the spec's exact contract (id, version,
`min_kandev_version`, `runtime`, `ui`, `actions`, `config_schema`; no webhooks,
no capabilities), sync `Makefile` versioning, and validate the packaged
artifact on the host platform and all five platforms.

## Owned paths

- `manifest.yaml` (final contract)
- `server/manifest_test.go` (NEW — manifest-contract test; the plan's Tests
  section promises one and no other task owns it)
- `Makefile` (`VERSION` / `BIN` / `PKG_OUT` sync; confirm `test` target runs
  backend + bundle tests)
- `go.mod` / `go.sum` (verify; `go mod tidy` clean)
- `.github/workflows/ci.yml` (confirm the template's CI targets still match)

## Dependencies

Tasks 04 and 05.

## Acceptance

1. `manifest.yaml` matches the spec contract exactly: `id:
   "kandev-deepseek-credits"`, `display_name: "DeepSeek Credits"`,
   `description: "DeepSeek API balance and remaining credits in the session
   top bar."` (exact spec string),
   `author: "kandev"` (not the template's `"your-name-here"`),
   `repo_url: "https://github.com/kdlbs/kandev-plugin-deepseek-credits"`
   (the host renders this as the "Repo" link on the installed-plugin list;
   per task-02's transfer note the bootstrap may carry the author-owned
   fallback URL and must flip to this target at final packaging),
   `api_version: 1`, `version: "0.1.0"`,
   `min_kandev_version: "0.88.0"`, `categories: ["analytics"]` (matching
   `kandev-plugin-provider-usage`; not the template's `tools` default),
   five-platform `runtime.executables`,
   `ui.bundle: "/ui/bundle.js"`, one action `balance.get`
   `scope: workspace` — the current manifest field name; `resource_scope` is
   the pre-release legacy spelling accepted only for reading old records —
   `max_body_bytes: 1024`), and `config_schema` with `api_key` (`string`,
   `format: password`, `secret: true`, `title: "DeepSeek API key"` +
   description), `poll_minutes` (`number`, default 5, `minimum: 1`,
   `title: "Refresh interval (min)"` + description), `warn_below` (`number`,
   default 10, `title: "Warn threshold"` + description) — every property
   carries `title` because the Settings form labels fields with
   `title ?? key` and raw snake_case labels are not acceptable. No
   `webhooks`, no `capabilities`. Note: `minimum: 1` is declarative only —
   neither the host's config-schema validation nor the settings form parser
   implements the JSON-Schema `minimum` keyword, so the plugin's runtime
   floor clamp (task-04) is the enforcement point.
2. Makefile `VERSION` equals the manifest version and `PKG_OUT` derives the
   correct artifact name; `make test` runs `go test ./server/...` and the
   bundle tests; `make fmt`/`vet` are clean.
3. Archive contents are validated per package type: `make verify-package`
   (CI, all five platforms) yields exactly `manifest.yaml`, `ui/bundle.js`,
   the five `server/plugin-<os>-<arch>` binaries (`.exe` on Windows), and the
   generated internal `checksums.txt`; `make verify-package-host` (local fast
   loop) yields the same layout with exactly ONE host-platform binary
   (`plugin-pack -platform-only`). `checksums.txt` is generated by
   `plugin-pack`, never hand-authored. No recipe/development files leak in
   either archive.
4. `server/manifest_test.go` parses `../manifest.yaml` (plain YAML — the SDK's
   manifest package is `internal` to the kandev module and not importable from
   a plugin module) and asserts the exact contract: `id`,
   `display_name: "DeepSeek Credits"`,
   `description` exactly `"DeepSeek API balance and remaining credits in
   the session top bar."` (the spec's pinned string; a divergent-but-non-
   empty description is precisely the wrong-but-valid value this test
   exists to catch), `author` (`"kandev"`, NOT the template's
   `"your-name-here"`),
   `repo_url: "https://github.com/kdlbs/kandev-plugin-deepseek-credits"`
   (present and matching the target; the host renders it as the "Repo"
   link), `api_version: 1`,
   `version` matching a non-empty SemVer shape (`^[0-9]+\.[0-9]+\.[0-9]+$`),
   `min_kandev_version: "0.88.0"`, `categories:
   ["analytics"]`, the five `runtime.executables`, `ui.bundle`,
   `actions[0]` (`balance.get`, `scope: workspace`, `max_body_bytes: 1024`)
   AND `len(actions) == 1` (a second undeclared action must fail the test),
   `config_schema` fields with `api_key` marked `secret: true` AND
   `format: password` (the ONLY secret markers the host honors — a manifest
   dropping them stores the value in cleartext in `<id>.config.yml` and
   `GetMaskedConfig` returns it unmasked to the settings form, violating the
   spec's "never reaches the browser"), `poll_minutes` default 5 and
   `warn_below` default 10, `title` AND a non-empty `description` present on
   all three properties (the Settings form labels with `title ?? key` and
   shows the description as hint text), and the ABSENCE of `webhooks` and
   `capabilities`.
   This is load-bearing because `plugin-pack`/Install validate structure only —
   wrong-but-valid values (`min_kandev_version: "0.86.0"`, `categories:
   ["tools"]`, `max_body_bytes: 2048`, dropped secret markers or defaults)
   install cleanly — and because the base-floor CI job pins the SDK by a
   hardcoded ref (task-02 sets it to v0.88.0) with no mechanical coupling to
   the manifest declaration, so a floor regression (e.g. lowering
   `min_kandev_version` to 0.86.0) compiles clean at the pinned SDK and would
   go undetected without the test. `version` is shape-checked, NOT exact:
   the release workflow sed-bumps manifest.yaml + Makefile VERSION and then
   runs `make test` on the tag, so an exact `0.1.0` assertion would break
   the first release at publish time.

## Verification

```sh
make fmt
make vet
make test
make verify-package-host
tar tzf kandev-deepseek-credits-0.1.0.tar.gz
# CI: make verify-package  (all 5 platforms)
```

## Risks

- Template drift in the pack layout or CI targets; validate the archive
  contents explicitly rather than trusting the Makefile echo.
- `go mod tidy` must not strip entries needed by `plugin-pack`; keep running
  the pack from the SDK module context exactly as the template Makefile does.
